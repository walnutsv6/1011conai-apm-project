# Tetris ver2で検証した事例

この事例はゲーム固有の読み方を示す。数値は別のROMへ流用しない。スキルにはROM、実際の曲の転送記録、ゲームの画像を同梱しない。

元ROMは32KB、ヘッダータイトル `TETRIS`、グローバルチェックサム `$16BF`、SHA-256 `0d6535aef23969c7e5af2b077acaddb4a445b3d0df7bf34c8acef07b51b015c3`。

## 音楽と効果音

| 読み取ったもの | アドレス/制御 |
| --- | --- |
| 曲番号→ヘッダー | `$64B0` |
| 曲の初期化 | `$6B13` |
| 音符・フレーズ・終端・楽器 | `$6C44～$6D56` |
| 細かな音程変化 | `$6D67～$6DC9` |
| 音符→11bit周波数値 | `$6E02` |
| ノイズの設定表 | `$6E94` |
| SEの初期化・更新・APU転送 | `$6480～$6997` |
| 波形SE | `$6EA9 / $6ED9` |
| BGMの波形 | `$6EC9 / $6EE9` |

曲番号はタイトル3、A5、B6、C7、B-TYPE達成2、ゲームオーバー4。音符0はフレーズ終端、1は休符、`9D` は楽器3バイト、`Ax` は長さの指定。フレーズ列の `FFFF` はジャンプ。曲の終端は全チャンネルを停止する。

Aは50%矩形波と `$6EC9` の波形、Cは25%矩形波2声。他の曲は主に `$6EE9` の波形を使う。Bの波形パートは出力設定 `$A0` から、音の終了6フレーム前に `$40` へ変更する。

## 再発を避ける知見

- TYPE CのMUSICには2チャンネルしか保存されなかった。固定長と仮定して3番目を参照するとIndexError。実行時に空チャンネルを補完した。
- Bの波形フレーズに長さ指定に見えるバイトが連続する。原作は最初の長さ指定の直後に1バイトを音符として読む。一般的な再帰的トークン処理にすると波形パートだけ24フレーム長くなった。原作の命令の流れに従って修正した。
- BのCH1は最初の192フレームの休符と、その後の2112フレーム周期を分けて保存できる。他のパートは2112、ノイズは48フレーム周期。効果音復帰時に最初の192フレームを再生しない。
- ゲームオーバーをノイズSE1と推測したのは誤りだった。`$230F` は盤面の行転送中に鳴る行消去用の要求。ゲームオーバーはBGM/SE停止、盤面を埋める70フレームの待機、その後に曲4を要求する。
- 4ライン消去SEは24フレーム後にCH1からCH3へ連鎖し、合計56フレーム。初期パートの上書き時には未発火のCH3パートも取り消す。
- 包絡線で無音になっても、SEドライバーのカウンターが終わるまで優先順位による保護は残る。

## 今回の検証水準

音源制御は、検証専用の小さな命令実行器で元ROMのルーチンを実行した転送記録と比較した。SE14コマンドとBGM全6曲について全フレームを照合し、BGMは次のループでも比較した。全38サウンドバンクをネイティブPyxelで一時WAVへ出力し、音のある区間の非無音と休符区間の無音を確認した。ROM・解析モジュールを含めない配置での起動も検証した。

この方法で確認できるのは制御処理と出力の接続。120Hz/半音/8段階音量の丸め、ノイズの発振方式、位相、ステレオ・アナログ回路の差は残る。
